หน้าเครดิต — 4 ทิศทางดีไซน์

หน้า /dashboard/credits วันนี้คือแถวยอดเดียว + กล่องว่าง — ยังไม่เล่าเรื่อง "กระเป๋าเงินของร้าน" ให้ลูกค้าเข้าใจ ทั้ง 4 แบบจัดโครงต่างกัน: กระเป๋าเงินนำ · สมุดบัญชี · ฟีดกิจกรรม · แผงคู่ ข้อมูลจริงจาก API: ยอดรวมเดียว + รายการ type (เติมเงิน/ซื้อสินค้า/คืนเงิน/โบนัส) · amount (+/−) · description · วันเวลา เฟรม "มีรายการ" ใช้ข้อมูลตัวอย่างเพื่อดูผัง (ของจริงวันนี้: ยอด ฿0 ไม่มีรายการ — เฟรมสถานะว่างคือของจริง)

ทิศทาง: A · กระเป๋าเงิน B · สมุดบัญชี C · ฟีดกิจกรรม D · แผงคู่ มือถือ 320px หมายเหตุกลาง
A กระเป๋าเงิน — Wallet Card การ์ดยอดเด่น · คอลัมน์เดียว

ยอดเงินคือพระเอก — การ์ดกระเป๋าเงินการ์ดเดียวด้านบน (เรืองแสงส้มจางๆ ต่อเนื่องกับชิปเครดิตในรางซ้ายที่ผู้ใช้คุ้นอยู่แล้ว) ตัวเลขใหญ่แบบแอปธนาคารไทย ด้านล่างเป็นรายการเข้า–ออกเป็นการ์ดแถว สแกนเร็ว อ่านง่ายบนมือถือที่สุดในสี่แบบ

  • เล่าเรื่อง "กระเป๋าเงิน" ได้ทันที — การ์ดเดียวเห็นยอดใหญ่ ชัดเจนเหมือนแอปธนาคารที่คนไทยใช้ทุกวัน
  • ต่อเนื่องกับชิปเครดิตสีส้มในรางซ้าย — เห็นทีไรก็รู้ว่าคือเรื่องเดียวกัน
  • มือถือดีมาก: คอลัมน์เดียว ยอดใหญ่ แถวรายการสูงพอดีนิ้ว
  • ยอดเด่นตลอดแม้ตัวเลขเป็น ฿0 — หน้าว่างจะดู "โล่ง" กว่าแบบอื่น
  • แสดงรายการได้จำกัด ถ้าโหลดทีละ 10 แถวต้องมีปุ่มดูทั้งหมด/แบ่งหน้าชัดเจน
B สมุดบัญชี — Statement ตารางเข้า/ออก · มืออาชีพที่สุด

ยอดรวมอยู่หัวกระดาษ ส่วนรายการเป็น ตารางสมุดบัญชี แบ่งคอลัมน์ "เข้า" / "ออก" ชัดเจนแบบใบ statement ธนาคาร — ตาเห็นทิศทางเงินจากตำแหน่งคอลัมน์ทันที ไม่ต้องอ่านเครื่องหมาย +/− เหมาะกับผู้ใช้ที่ต้องการตรวจรายการเงีนจริงจัง

  • ดูเป็นมืออาชีพที่สุดในสี่แบบ — โครง statement คือมาตรฐานสากลของ "ใบรายการเงิน"
  • คอลัมน์เข้า/ออกแยกตำแหน่ง ตรวจรายการเร็ว รวมยอดทางขวางอยู่ที่เดิมทุกแถว
  • รองรับรายการเยอะได้ดีที่สุด — แถวบาง อ่านได้รวดเดียวหลายรายการ
  • สแกนจอกว้างคุ้ม; คอลัมน์วันที่ + ยอดใช้ตัวเลขกึ่งกลางคอลัมน์ ไม่กระโดด
  • บนมือถือตาราง 4 คอลัมน์ต้องยุบ (ซ่อนคอลัมน์วันที่เหลือวันเดือนสั้น หรือพับเป็นการ์ด)
  • อารมณ์ "ธนาคาร" มาก — ถ้าต้องการความเป็นมิตร/สนุกแบบร้านเกม แบบ A หรือ C เหมาะกว่า
C ฟีดกิจกรรม — Activity Timeline จัดกลุ่มตามวัน · ไอคอนประเภท

รายการเป็น ฟีดแบบแอปมือถือ — จัดกลุ่มด้วยหัววัน (วันนี้ / เมื่อวาน / วันที่) แต่ละรายการมีไทล์ไอคอนตามประเภท (เติมเงิน/ซื้อ/คืนเงิน/โบนัส) ให้ "รู้เรื่องเงินก่อนอ่านตัวอักษร" ยอดรวมวางเป็นแถบเงียบๆ ด้านบน ให้ฟีดเป็นตัวเอก — เป็นกันเองแบบร้านเกมที่สุดในสี่แบบ

  • อ่านเป็นเรื่องราว — หัววัน + ไอคอนประเภท ทำให้เล่า "เงินวิ่งยังไงบ้างช่วงนี้" ได้ทันที
  • ดูเป็นมิตรและเป็นร้านเกมที่สุด — ไม่หนักธนาคารเกินไป
  • เวลาในฟีดเหลือแค่ชั่วโมง (วันที่อยู่ที่หัวกลุ่ม) — แถวสั้น อ่านสบายตา
  • โครงฟีดยืดหยุ่นรับประเภทใหม่ (คืนเงิน/โบนัสเมื่อ backend มี) โดยเพิ่มไอคอนเดียว
  • กินความสูงมากที่สุด — หน้าจอเดียวเห็นรายการน้อยกว่าแบบ B พอสมควร
  • การจัดกลุ่มวันเป็น logic ฝั่ง client เพิ่มจากของเดิม (ข้อมูล createdAt มีจริง แค่ต้องจัดเอง)
D แผงคู่ — Wallet Desk แผงสรุปตรึงซ้าย · ต่อเนื่องกับ Order Desk

ภาษาเดียวกับหน้ารายละเอียดคำสั่งซื้อแบบแผงคู่ — แผงซ้ายตรึงบอก "เครดิตคืออะไร มีเท่าไหร่ มาจากไหน" ขวาเป็นรายการเต็มความกว้าง สองข้อมูลอยู่ในสายตาพร้อมกันตลอด เหมาะกับ desktop และคนที่จัดการหลายอย่างพร้อมกัน

  • อธิบาย "เครดิตคืออะไร" ได้ครั้งเดียวตลอดกาล — แผงซ้ายมีที่พื้นสำหรับคำอธิบาย + เข้า/ออกล่าสุด
  • ภาษาโครงเดียวกับหน้า order detail (แผงคู่) — dashboard ทั้งพื้นที่มีเสียงเดียวกัน
  • ยอด + สรุปอยู่ตลอดขณะเลื่อนดูรายการยาวๆ
  • บนมือถือแผงซ้ายต้องตกลงไปอยู่บนสุด/ล่างสุด — สูญเสียจุดขาย "ตรึงตลอด"
  • คอลัมน์รายการแคบลงเพราะแบ่งพื้นที่กับแผงซ้าย
M มุมมองมือถือ 320px — ทั้ง 4 แบบ เลื่อนแนวนอนเทียบ

เครดิตเป็นหน้าที่คนเปิดน้อยแต่เปิดตอน "อยากรู้แน่ๆ" — ส่วนใหญ่จากมือถือ แบบไหนย่อแล้วยอดยังชัดและรายการยังอ่านออก คือแบบที่ใช้ได้

  • A เก็บงานมือถือได้เนียนสุด — การ์ดยอดย่อขนาดแล้วยังเด่น แถวรายการพอดีจอ
  • B ต้องยุบตาราง — 4 คอลัมน์ไม่ลง 320px ต้องพับเป็นแถว (ดูตัวอย่าง) ซึ่งก็ยังอ่านได้ดี
  • C เกิดมาจากมือถือ — ฟีด + ไทล์ไอคอนทำงานเหมือนเดิมทุกอย่าง
  • D เสียมากที่สุด — แผงตรึงกลายเป็นการ์ดธรรมดา จุดขายหายไป

หมายเหตุกลาง — ใช้ร่วมกันทุกแบบที่เลือก

  • ข้อมูลจริงที่ API มี: ยอดรวมเดียว (balance + currency THB) และรายการ type · amount (+/−) · description · วันเวลา — ทุกแบบใช้แค่นี้ ไม่มีการเดา
  • ข้อจำกัดจริงของ backend ที่ทุกแบบเคารพ: ไม่มี flow "เติมเครดิต" ในหน้าเว็บ (backend มี method เติมแต่ไม่มี endpoint ให้ user เรียกเอง) — จึงไม่มีแบบไหนใส่ปุ่มเติมเงิน/QR ให้กดเล่น; backend สร้างรายการจริงแค่ TOPUP กับ PURCHASE — ส่วน REFUND/BONUS เป็นประเภทที่ UI เตรียมรองรับ (มี label ไทยแล้ว) แต่ยังไม่มี flow สร้างจริง
  • สถานะว่างคือของจริงวันนี้ (ยอด ฿0) — ทุกแบบยกระดับจากกล่องข้อความเปล่าเป็นการอธิบายว่า "เครดิตจะมาจากไหน" พร้อมชิปประเภทที่ระบบรองรับ
  • field ที่ frontend ยังไม่ได้ใช้: referenceId (โค้ดอ้างอิงคำสั่งซื้อของรายการ PURCHASE) — ถ้าเลือกแบบไหน แนะนำเพิ่มเข้า type แล้วทำ description เป็นลิงก์เปิดออเดอร์ได้ทันที
  • สีเขียว/ส้มที่เห็นในเฟรม ใช้ token จริงหลังแก้ @theme (status-success กลับมาทำงานแล้วตาม commit ล่าสุด)
  • การจัดกลุ่มวัน (แบบ C) และ "เข้า/ออกล่าสุด" (แบบ D) คำนวณฝั่ง client จากข้อมูลที่มีอยู่ — ไม่ต้องแตะ backend
  • ปุ่มแบ่งหน้า ใช้ Pager เดิมที่มีอยู่แล้ว (แบบ B ฝังใน footer ของสมุดบัญชี, แบบ A/C/D ใช้ปุ่มโหลดเพิ่ม/ดูทั้งหมด)
